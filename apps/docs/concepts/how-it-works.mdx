---
title: "How Hookfish works"
description: "Understand connection paths, trusted providers, authorization, and secret access."
---

Hookfish exposes one connection abstraction for OAuth tokens and static
credentials. Trusted server code asks for access to a path. Hookfish either
returns a usable secret or reports what the user must authorize.

## Connection identity

A connection path is `namespace/providerId`:

```text
user/personal/gmail
user/personal/gmail/mcp
service/prod/openai/secret
```

The final segment always selects a trusted provider implementation. Everything
before it is the namespace. Provider IDs are slash-free, non-reserved
lower-camel JavaScript identifiers such as `gmail`, `githubEnterprise`, `mcp`,
or `secret`.

Folder names may equal provider names. Their position removes ambiguity. In
`user/personal/gmail/mcp`, `gmail` is a namespace segment and `mcp` is the
provider ID.

Hookfish stores identity as `(organization, namespace, providerId)` with a
unique constraint. It does not accept caller-generated opaque IDs, slots,
or provider templates in request bodies.

## One access operation

```ts
const { secret } = await hookfish.connections.access(
  'user/personal/gmail',
)
```

For a usable connection, Hookfish returns `{ path, secret, scopes, expires_at,
refreshed }`. For an OAuth-backed connection that is not ready,
`@hookfish/sdk` throws `HookfishError` with:

```json
{
  "code": "authorization_required",
  "authorize_url": "https://provider.example/authorize?...",
  "expires_at": "2026-08-12T18:00:00.000Z"
}
```

Each unready access creates new state, PKCE material when required, and a fresh
authorization URL. It supersedes earlier pending URLs for that connection.
For MCP connections, `mcpAuthProvider` reports an upstream `401` to Hookfish,
which starts fresh authorization even if the stored expiration has not passed.

## Lifecycle

<Steps>
  <Step title="Resolve the provider">
    Hookfish parses the final path segment and resolves only that trusted
    provider implementation.
  </Step>
  <Step title="Ensure the connection">
    Hookfish creates the structured connection if it does not exist. Supplying
    different immutable configuration later returns `409`.
  </Step>
  <Step title="Return or acquire a secret">
    Static providers read an encrypted value set with `setSecret`. OAuth
    providers refresh when possible, otherwise return `authorization_required`
    with a new URL.
  </Step>
  <Step title="Complete authorization">
    The public callback claims single-use state, exchanges the code, encrypts
    the returned credentials, and marks the connection ready.
  </Step>
  <Step title="Disconnect">
    Hookfish attempts upstream revocation when supported and deletes the local
    connection.
  </Step>
</Steps>

## Connection-owned state

Each connection owns its non-secret configuration, OAuth client fallback
credentials when needed, user token, refresh token, and metadata. Hookfish
does not create shared runtime provider records.

For dynamic MCP connections, the built-in `mcp` provider uses the connection's
URL to discover the protected resource and authorization server. It prefers a
deployment-level Client ID Metadata Document (CIMD) when advertised and uses
Dynamic Client Registration (DCR) only as a compatibility fallback. Any DCR
credentials belong to that connection.

## Security boundary

`connections.access()` and `connections.setSecret()` are server-only. The
optional browser facade exposes connection metadata and disconnect operations,
never usable credentials or authorization starts. Authenticate your own
application endpoint before calling Hookfish with a scoped broker token.
