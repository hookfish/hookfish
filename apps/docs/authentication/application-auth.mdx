---
title: "Application authentication"
description: "Use Hookfish with the authentication and authorization already built into your application."
---

Hookfish does not replace your application's authentication provider. Your
existing backend verifies the user, authorizes the requested operation, and
then calls Hookfish with a server-side credential.

```text
Browser or application client
  → your existing authenticated endpoint
  → your authorization policy
  → Hookfish SDK with a server-side broker credential
  → Hookfish API
```

The browser sends only its normal application session. Never return a Hookfish
broker credential or a provider secret to browser code.

## Add Hookfish to an authenticated endpoint

Verify the session exactly as you do for the rest of your application. Derive
the connection path from trusted session data instead of accepting an arbitrary
path from the request.

```ts
import { Hookfish, HookfishError } from '@hookfish/sdk'

const hookfish = new Hookfish({
  apiKey: process.env.HOOKFISH_API_KEY!,
  baseUrl: `${process.env.HOOKFISH_URL}/api`,
})

export async function GET(request: Request) {
  const session = await verifyApplicationSession(request)
  if (!session) {
    return Response.json({ error: 'Sign in required.' }, { status: 401 })
  }

  const basePath = resolveBasePath(session)

  try {
    return Response.json(
      await hookfish.connections.list({ namespace: basePath }),
    )
  } catch (error) {
    if (error instanceof HookfishError) return error.getResponse()
    throw error
  }
}
```

Apply your normal permission checks before listing, authorizing, accessing, or
disconnecting a connection. Successful `connections.access()` responses
contain credentials and must remain in trusted server code.

## Choose a base path

`resolveBasePath` is an application function, not an identity-provider
requirement. It returns the canonical Hookfish subtree that your endpoint may
address.

A single-tenant application can return a constant:

```ts
export function resolveBasePath(_session: ApplicationSession) {
  return 'global'
}
```

A multi-tenant application can use an organization, workspace, account, or any
other identifier already verified by its authorization layer:

```ts
export function resolveBasePath(session: ApplicationSession) {
  return `organizations/${session.activeOrganizationId}`
}
```

Hookfish preserves this path. It does not require a `tenant:` prefix or rewrite
the resource into a hidden namespace.

## Use your existing provider

Better Auth, Clerk, WorkOS, Auth0, Auth.js, and custom session systems all use
the same integration boundary:

1. Verify the request with the provider's server SDK.
2. Apply your application's authorization policy.
3. Resolve a constant or session-derived base path.
4. Call Hookfish from the server using paths beneath that base.

Auth0 Organizations are optional. Without Organizations, return a constant
base path or derive one from another trusted application claim. The same rule
applies to every provider: Hookfish does not impose an organization model.

## Limit the broker credential

The root key can address every Hookfish resource. Keep it in a trusted secret
manager and use a scoped, expiring broker token when a service needs only one
path or subtree.

For example, a service restricted to one application account can receive the
scope `accounts/acc_123/**`. Hookfish rejects attempts to address resources
outside that subtree even if the application contains a path-handling bug.

See [Scoped broker tokens](/authorization/token-scoping) for token creation and
delegation rules. Framework-specific examples are available for
[Next.js](/frameworks/nextjs) and [Hono](/frameworks/hono).
